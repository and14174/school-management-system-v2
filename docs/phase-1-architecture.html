01The shape of the thing

Build a modular monolith: one deployable backend, one database, but internally split into modules with hard boundaries — separate Postgres schemas, no cross-module table reads, and a published contract for every module that another module is allowed to call.

This is the right call for Phase 1 because the domain boundaries are still moving. Microservices would force you to guess where attendance ends and gradebook begins before you have a customer, and would make the cross-cutting requirements in the brief — audit logs, tenant isolation, the automation engine, year rollover — dramatically harder. The boundaries you enforce in code are the same ones you'd extract along later if a module genuinely needs its own scaling profile (report generation and messaging are the likely first candidates).

The one-sentence version

Nx monorepo → NestJS backend on Fastify, one module per bounded context, each owning its own Postgres schema → Postgres 18 with row-level security as the tenant backstop → Next.js 16 front end where the four portals are route groups over one shared component library.

The boundary rules that make this work

  • Every module owns a Postgres schema (people, attendance, gradebook…). Its DB role has no grants on other modules' tables — the boundary is enforced by the database, not by discipline.
  • A module exports one *.contract.ts — an interface plus its event types. Nx tag rules fail the build on any import that reaches past it.
  • Reads across modules go through the contract; writes across modules go through events. No module writes another's tables, ever.
  • Reference IDs cross boundaries, not entities. attendance stores a person_id; it does not store a copy of the student's name.
  • Dashboards and reports read from read models — materialised views or projection tables owned by reporting — so a principal's dashboard doesn't fan out into nine modules per page load.

04The six calls that are expensive to reverse

Almost everything else can be refactored later. These six get baked into every table and every query, so decide them before writing the first migration.

1 — One person, one record

A single people.person row per human, with role assignments layered on top. A parent who teaches at the school and has two children enrolled is one person with three roles, not three records.

-- schema: people
person(id, tenant_id, given_name, family_name, dob, photo_file_id, custom_fields jsonb, …)
person_role(person_id, role, campus_id, valid_from, valid_to)   -- student|guardian|staff|alumni
household(id, tenant_id, name, primary_address_id)
household_member(household_id, person_id, relationship, is_primary_contact)
relationship(from_person_id, to_person_id, type, has_custody, may_pickup, may_receive_comms)

Duplicate detection runs on normalised name + DOB + contact trigrams (pg_trgm) at create time and as a batch job; merges are recorded so they can be undone.

2 — Everything is effective-dated

The single most common failure in school systems: last year's report card changes because a student moved class this year. Enrolments, section memberships, staff assignments, fee plans and role assignments all carry valid_from / valid_to, and every academic fact is stamped with the academic_year_id it belongs to. Use Postgres 18 temporal PRIMARY KEY / FOREIGN KEY constraints to stop overlapping periods at the database level. Historical records are immutable; corrections create a new version and an audit entry.

3 — Ambient context on every request

Tenant, campus and academic year are resolved once per request and never passed as query parameters a client could tamper with. They live in an AsyncLocalStorage context, are asserted by a Nest interceptor, and are pushed into the DB session so RLS can see them.

4 — Custom fields as JSONB, never EAV

A field_definition registry per tenant per record type drives a Zod schema built at runtime; values live in a custom_fields jsonb column with a GIN index. Entity–attribute–value tables will make every report unwritable by month six.

5 — Rules are configuration rows, not code branches

Attendance rules, grade scales, calculation rules, promotion criteria and report-card templates are versioned config rows scoped to tenant + academic year. When a school changes its grading scale mid-year, last year's grades must still resolve against the old scale — which only works if the scale is a row the grade points at.

6 — Every mutation is auditable and bulk operations are reversible

A generic trigger writes before/after row images to audit.record_history. Every bulk import or bulk edit creates a bulk_operation row that groups its changes so it can be rolled back as a unit. This is one of the brief's stated differentiators and it is nearly free if you build it first, nearly impossible to retrofit.

Retrofit cost

Adding effective dating or the audit trigger after twenty modules exist means rewriting every query and backfilling history that was never recorded. Build both in the first milestone, before the first domain module. Section 11 covers how to execute each of the six and how to stop them eroding.

05Tenancy, permissions and the request path

Shared schema with a tenant_id on every tenant-scoped table, application-level filtering as the first line of defence, and Postgres RLS as the backstop that holds even when application code has a bug. The app connects as a role without BYPASSRLS; migrations run as a separate owner role.

Permission model

A permission is action × resource × scope × fields. Scope is the piece most systems get wrong: a teacher reads attendance for their own sections, a head of year for their grade level, a nurse reads medical for all students but no grades at all. Model scope explicitly as own | section | grade_level | campus | tenant and let tenants compose roles from it.

06How modules talk — the outbox

Synchronous calls go through injected contract interfaces. Anything that fans out — notifications, read-model updates, webhooks, automation rules — goes through a transactional outbox, which is the single most valuable piece of plumbing in the system.

-- one transaction
INSERT INTO attendance.record (…);
INSERT INTO platform.outbox (topic, payload, tenant_id)
     VALUES ('attendance.marked_absent', '{"person_id":…,"date":…}', …);
COMMIT;

-- a worker drains the outbox and dispatches to:
--   notifications  → "unexplained absence" message to guardians
--   reporting      → attendance read-model projection
--   integration    → registered webhook subscribers, with retry
--   automation     → "5 absences this month → alert counsellor" rule (Phase 2)

Because the event is written in the same transaction as the fact, you never notify a parent about an absence that got rolled back — and you never silently lose a notification because Redis was down. The automation engine in Phase 2 and the webhook platform become consumers of a stream that already exists, rather than new infrastructure.

10What not to build in Phase 1

Each of these is a product in its own right. Integrate, stub, or defer — and say so explicitly in the roadmap so it doesn't creep back in.

  • Automated timetable generation. Constraint optimisation. Manual scheduling with good conflict detection covers Phase 1; solve the solver later.
  • A full LMS. Assignments, submissions and feedback only. Integrate Google Classroom and Teams.
  • General-ledger accounting and payroll. Billing stays a subledger with a clean export.
  • Delivery infrastructure. Email, SMS, WhatsApp, push and payments are provider adapters, never in-house.
  • E-signature, proctoring, plagiarism, bus GPS, biometric hardware. Adapter interfaces at most.
  • AI features. Every one of them depends on clean data that doesn't exist yet. The outbox stream is what makes them cheap in Phase 3 — and anything touching assessment, discipline, admissions or safeguarding needs a human in the loop by design, not by policy.

The brief is right that the segment choice shapes the roadmap — that decision is closed in section 12.

11Executing the six

The six calls in section 4 are only worth anything as mechanisms. Here is what each one actually becomes, when it lands, and the test that proves it still holds.

1 — One person, one record M2

The person table is the easy part. Three things hanging off it are what teams get wrong:

  • Account is not person. identity.account links many-to-one to people.person. A young student is a person with no account; a guardian is one account resolving to one person, whose relationships grant access to N students. That link is what delivers the single family login — not a bespoke parent-portal table.
  • Merges leave tombstones. Never hard-delete the losing row. Keep it with merged_into_id and resolve old IDs in the repository layer, so existing URLs, exports and external integrations keep working after a merge.
  • External IDs get their own table. person_identifier(type, value) — student number, national ID, previous-school ID. One overloaded column is what stops you onboarding a second country.

Prove it: put “the parent who also teaches and has two children enrolled” in the M2 seed. Any query that breaks on that fixture has regressed.

2 — Effective dating, applied selectively M1 pattern

Blanket effective-dating is expensive and over-applied. Sort every table into one of three buckets once, and record the bucket in the schema file:

BucketShapeExamples
Year-scopedBelongs to exactly one year, frozen after close. academic_year_id + natural date.Grades, attendance, enrolment records, invoices
Effective-datedvalid_from/valid_to, with a Postgres 18 temporal PRIMARY KEY … WITHOUT OVERLAPS.person_role, section_enrollment, staff_assignment, household_member, addresses, fee-plan assignments
Current-stateNo dating; audit history covers change over time.Config lookups, UI preferences, templates

Skip full bitemporality — the audit log already gives you transaction time. The real enforcement mechanism is year close: academic_year.status = open | locked | archived, with locked years rejecting writes by trigger. That, not developer discipline, is what protects last year's report cards. Put asOf(date) in the shared db library; if anyone hand-writes the date predicate they will eventually forget it.

Prove it: a “student changes section in March” fixture; assert the Term 1 report card is byte-identical before and after the move.

3 — Ambient context M1

The context belongs to the transaction, not the request. One helper — withTenantTx() — opens the transaction, issues the SET LOCAL, runs the callback. Then an ESLint rule banning raw db.* access outside it.

The bug that ends the company

SET LOCAL is transaction-scoped and safe behind pgbouncer in transaction mode. Plain SET is session-scoped and will leak one tenant's context onto another tenant's request through a pooled connection. Lint for it.

Keep the three context values in their proper roles: tenant is security (RLS enforces it), campus is authorization (a CASL scope), year is a filter. Conflating them makes cross-campus reporting impossible later.

Prove it: a generated negative suite that calls every repository method with tenant A's context asking for tenant B's IDs and asserts empty. Generated over the repository registry — hand-written coverage decays.

4 — Custom fields M2 registry · M6 reporting

field_definition(tenant_id, entity_type, key, data_type, options, validation, reportable) compiles to a cached Zod schema per tenant and entity type, invalidated on definition change. Values live in custom_fields jsonb with a jsonb_path_ops GIN index. Two rules keep it from rotting:

  • Don't chase fast ad-hoc JSONB reporting. Let a definition be flagged reportable and materialise only those into typed columns in the read model.
  • A custom field may never be a foreign key or drive business logic. The moment a school wants a custom field other features must react to, it is a real field and needs a migration. Put that sentence in the contributing guide.

5 — Rules as configuration M1 pattern

The whole trick is one line: facts point at the rule version, not the rule. grade.grade_scale_version_id. Versions are immutable; editing creates a new one. That is what makes a mid-year scale change safe.

The larger leverage is to implement rules as data interpreted by a small evaluator — a tiny JSON DSL of conditions and actions — never JavaScript stored in the database. One evaluator then serves grading rules, attendance rules, promotion criteria, the workflow engine's conditional fields and the Phase 2 automation engine. Teams routinely build three separate evaluators for these; it is pure waste. Golden-file tests per rule version.

6 — Audit and reversibility M1

Two distinct mechanisms — don't merge them:

  • Row history. One generic trigger function attached to every table by a migration helper, writing before/after JSONB plus changed_by, tx_id, request_id, bulk_operation_id. Partition by month from day one — it becomes your largest table by an order of magnitude. Per-table column exclusion lists so tokens and counselling-note bodies never land in history.
  • Access log. Who read medical, counselling or safeguarding data. Triggers cannot see reads, so this is emitted app-side from the serialisation interceptor whenever a response includes a restricted field.

Undo works because bulk_operation groups changes through a session GUC the trigger reads. Reversal replays before-images backwards in one transaction and records itself as a new bulk operation. Offer undo only when no later change has touched those rows — checkable straight from the history sequence.

What makes all six stick

Five CI checks, written in M1, that query the database's own catalogs. Without these the six are a document nobody re-reads.

  1. Every tenant-scoped table has tenant_id and a policy — diff pg_policies against information_schema.tables.
  2. Every table has the audit trigger attached — assert from pg_trigger.
  3. No table is owned by the app role, and the app role lacks BYPASSRLS.
  4. The generated cross-tenant negative suite passes.
  5. Nx module-boundary lint passes.

12Decisions, closed

Segment: private and international schools as one beachhead

Take private and international together and defer public districts. The two share everything that actually closes a sale — admissions, tuition and payment plans, family experience, multiple languages, multi-campus — so one roadmap serves both.

Districts are a different business, not a bigger one. Certified compliance reporting and Ed-Fi/OneRoster are table stakes before the first sale, on a 12–18 month cycle: a large fixed cost paid entirely ahead of revenue, and it would reshape M7–M8 around reporting packs instead of billing and family experience. Reverse this only if most of the schools you can already reach are public — in which case swap M7 and M8 and add a compliance module.
